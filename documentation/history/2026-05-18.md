# 2026-05-18

## Done

- Fixed conflict with the **pane-relief** community plugin that produced a blank Time Machine panel and a console crash (`Cannot read properties of undefined (reading 'createDiv')`) when activating the view. Reported in GitHub issue #5 by PowerSchill (macOS Tahoe).
- `src/app/ui/time-machine-view.ts:29` — renamed the private field `headerEl` to `tmHeaderEl`. The corresponding spec at `src/app/ui/time-machine-view.spec.ts:84` was updated.

## Root cause

`TimeMachineView extends ItemView` and declared `private headerEl!: HTMLElement` as a class field. With `target: ESNext` and `useDefineForClassFields: true` (the default Bun/TS behavior for this config), a bare class-field declaration emits as `this.headerEl = undefined` immediately after `super()`. That overwrites the element Obsidian's `ItemView` constructor stores at `this.headerEl`.

The pane-relief plugin monkey-patches `ItemView.prototype.load` (see `maximizing.ts`) to re-add the pre-1.6 drag-handle icon:

```ts
if (!this.iconEl) {
    const iconEl = this.iconEl = this.headerEl.createDiv("clickable-icon view-header-icon")
    ...
}
return old.call(this)
```

Because our class clobbered `headerEl` with `undefined`, the patched `load` crashed before reaching `old.call(this)`, leaving the leaf without its `onOpen` ever firing → blank pane. Disabling pane-relief masked the symptom but the underlying shadowing bug was on our side.

Other inherited fields we touch (`contentEl`, `containerEl`) were never shadowed by accident because we picked distinct names (`contentAreaEl`, etc.); the only collision was `headerEl`. `override navigation = false` is intentional and remains.

## Follow-up

- Worth filing an upstream issue against pjeby/pane-relief: the `ItemView.prototype.load` patch should null-check `this.headerEl` (and ideally call `old.call(this)` first so Obsidian initializes its DOM before pane-relief decorates it).
